# Known bugs

Found during the P4–P6 build and the frontend build, verified against a running instance on
2026-09-08. Every entry below was reproduced, not inferred from reading code.

Ordered by severity. Nothing here is fixed; the fixes are suggestions, not work done.
B8 was found while writing the README and verifying its example payloads.

---

## B1 — A consent sent as `false` counts as answered, and the application submits

**Severity:** high — an application can be submitted with every consent explicitly refused.

`SectionValidator` decides a field is absent when the value is null or blank. `false` is
neither: `String.valueOf(false)` is `"false"`, so a `CONSENT` field declared `required: true`
passes layer 1 when the client sends `false`. Layer 2 (`SubmissionValidator`) only inspects
`creditCheck`, so the other four consents are never checked again by anything.

**Reproduce**

```bash
# ... with a draft completed through paymentDetails ...
curl -X PUT localhost:8080/api/applications/$TOKEN/sections/consent \
  -H 'Content-Type: application/json' \
  -d '{"informationConfirmed":false,"termsOfService":false,"dataProcessing":false,
       "privacyNotice":false,"creditCheck":{"version":"x","acceptedAt":"2099-01-01T00:00:00Z"}}'
# -> 200

curl -X POST localhost:8080/api/applications/$TOKEN/submit
# -> 200, a reference is minted
```

The stored blob then reads `"termsOfService": false` on a SUBMITTED application.

**Why it matters.** The browser form never does this — it omits unchecked consents so that
`REQUIRED` fires. But there is no authentication, so the form is not a control. This is
exactly the case layer 2 exists for, and it misses it.

**Suggested fix.** Give `CONSENT` a type-aware check in `SectionValidator`: a required
consent is satisfied only by an acceptance record or a literal `true`, never by anything
else. `SubmissionValidator.isAccepted` already encodes that rule for `creditCheck` — layer 1
should apply the same test to every consent in the section.

## B2 — Consent `version` and `acceptedAt` are whatever the client says

**Severity:** high — the stored record of *which* consent text was accepted, and *when*, is
unauthenticated client input.

Each consent is stored as `{version, acceptedAt}` (A11). The flow definition declares the
version (`de-schufa-2026-01`), but nothing compares the submitted version to it, and
`acceptedAt` is generated by the browser's clock and stored verbatim.

**Reproduce.** The B1 request above stores, on a submitted application:

```json
"creditCheck": { "version": "not-a-real-version", "acceptedAt": "2099-01-01T00:00:00Z" }
```

**Why it matters.** A11's whole argument for storing only a version identifier is that the
identifier tells you which text the applicant agreed to. An identifier the applicant chooses
tells you nothing. A future-dated acceptance is not a plausible clock skew — it is simply
unvalidated input in the field that would matter most if the consent were ever questioned.

**Suggested fix.** The server should write both: on save, replace any submitted consent
record with `{version: <from the flow definition>, acceptedAt: <server clock>}`. The client
then only says *whether* a box was ticked, which is the only part it is entitled to assert.
This also removes the client clock from the record entirely.

## B3 — A failed `localStorage` write is swallowed, and the draft becomes unreachable forever

**Severity:** high — silent data loss, and the UI promises the opposite.

`store.setToken` catches and discards the failure:

```js
setToken(token) {
    try { localStorage.setItem(TOKEN_KEY, token); } catch { /* private mode: resume is simply unavailable */ }
}
```

The draft token is the only way back into an application: the resume link is written to the
outbox and never sent (A18). If the write fails, the row exists and nobody can ever reach it.

**Reproduce.** In a private window, or with `Storage.prototype.setItem` stubbed to throw:

| Storage state | What happens |
|---|---|
| empty (fresh private window) | "Start application" creates the draft, then returns to the landing page with **no error**. Clicking again creates another orphan. |
| holds a stale token | You are silently dropped into the **older** application instead of the one you just started — a different country's form, someone else's earlier draft on a shared machine. |

Both were reproduced; the orphaned rows are in the database with `status = DRAFT` and
`last_completed_step = NULL`, unreachable.

**Related:** the step screen says *"Your progress is saved after every step"* while sitting
directly above the fields being typed into. Input on the current step is deliberately not
saved (T-2/A16), so the placement invites the wrong reading even when storage works.

**Suggested fix.** Probe storage at `createDraft` by writing and reading back. When it does
not work, hold the token in memory for the session and show the `resumeUrl` the API already
returns — "save this link, it is the only way back" — in place of the save promise. Roughly
fifteen lines, and it turns silent loss into a usable flow without changing the copy.

## B4 — The token view omits the reference, so a submitted application is a dead end

**Severity:** medium.

`GET /api/applications/{draftToken}` returns `status, country, email, lastCompletedStep,
resumeStep, formData, flow` — no `reference`. When the token belongs to an application that
is already submitted (a second tab, or a crash between submitting and clearing storage), the
client can see that it is `SUBMITTED` but cannot show the reference. The UI sends the
applicant to the lookup screen with nothing to type into it.

**Reproduce.** Submit an application, restore its token to `localStorage`, reload.

**Why it matters.** The token holder is already authorised to see the whole application,
including every field of it. Withholding only the reference protects nothing and strands
the one person entitled to it.

**Suggested fix.** Add `reference` and `submittedAt` to `ApplicationView`; have the client
route a submitted token straight to the success screen.

## B5 — Email is specified as editable, and cannot be edited

**Severity:** medium — an unimplemented domain rule, not a defect in what was built.

CLAUDE.md: *"Email is captured at the same time and IS editable."* ASSUMPTIONS A7 spells out
why (a mistyped address must be recoverable). `Application.changeApplicantEmail` exists and
enforces the draft-only rule — and nothing calls it. There is no endpoint and no UI.

**Consequence.** A typo in the address at step 0 is unrecoverable in the intended sense: the
applicant can only start again, and the abandoned draft still holds their address.

**Suggested fix.** `PATCH /api/applications/{draftToken}` accepting `{email}`, normalised
through the same path as `createDraft`, plus an edit control on the review screen.

## B6 — Derived record accessors leak into the flow API

**Severity:** low — unintended public surface.

Jackson serialises bean-named accessors on records alongside the components, so every field
in `GET /api/flows/*` carries two properties that are internal helpers:

```json
{ "name": "firstName", "type": "TEXT", "required": true,
  "alwaysRequired": true, "choice": false }
```

`FieldDefinition.isAlwaysRequired()` exists for `SubmissionValidator`; `isChoice()` for
readability. Neither was meant to be in the contract, and a client that starts depending on
them makes them impossible to remove.

**Suggested fix.** `@JsonIgnore` on both, or move them to the callers that use them.

## B7 — The compose stack cannot demonstrate resume

**Severity:** low — affects the demo path only.

`docker-compose.yml`'s `app` service sets the datasource variables but not
`SPRING_PROFILES_ACTIVE`, so `DevOutboxController` is not registered and
`GET /api/dev/outbox` returns 404. Since no email is ever sent, the outbox is the only way to
see a resume link — so `docker compose up` cannot show the feature the outbox exists for.

**Suggested fix.** `SPRING_PROFILES_ACTIVE: dev` in the `app` service's `environment:`. The
compose file is the local stack, and it already hardcodes database credentials.

## B8 — Every error body echoes the draft token

**Severity:** low–medium — a bearer credential is reflected into a payload built for sharing.

`ProblemDetail` is created with `ProblemDetail.forStatus(...)`, which leaves `instance` unset;
Spring MVC then fills it from the request URI. Because the draft token is a path segment, every
4xx from a draft-scoped endpoint returns it:

```json
{
  "type": "https://onboarding.zalando.com/problems/validation-error",
  "status": 400,
  "instance": "/api/applications/I-hrt3Jk0qNC-n0XomxFItP1YHe4JpL35k72z4O8U1o/sections/personalDetails",
  "requestId": "91125645-8bea-4d82-8d16-ca373e04ebf8"
}
```

**Reproduce.** Any failing section save: `PUT /api/applications/$TOKEN/sections/personalDetails`
with an invalid payload.

**Why it matters.** The caller already knows its own token, so this is not a disclosure to a
third party by itself. But problem bodies are the things people paste into support tickets and
that client-side error reporters ship to third parties, and `requestId` exists precisely so
that neither has to carry the credential. Reflecting the token undoes that.

**Suggested fix.** Set `instance` explicitly to something safe — the route template
(`/api/applications/{draftToken}/sections/{sectionId}`) or simply omit it — in the one place
problem bodies are built (`ProblemDetailsAdvice.problem`).

## Fixed during the frontend build, listed for the record

Not open — noted so a reviewer reading the diff knows why these changed.

- **Redirect notices were invisible.** A gating refusal set a message, and the redirect
  target's own render immediately cleared it, so the applicant was bounced with no
  explanation. Notices are now deferred and flushed once per route.
- **Editing from Review marched the applicant forward again.** Correcting step 2 led to
  steps 3, 4, 5, 6 rather than back to Review. The client now follows the `resumeStep` the
  save response already returns.
- **Static assets had no `Cache-Control`.** `index.html`, `app.js` and `styles.css` carry no
  hash in their filenames, so browsers cached them heuristically and served a stale `app.js`
  after a deploy. Now `no-cache`, which revalidates on every load.
- **The submitted-email uniqueness pre-check matched the application against itself.** Two
  simultaneous submits of one draft could make the loser report `EMAIL_ALREADY_SUBMITTED`
  instead of returning the winner's reference. Now excluded by id.
